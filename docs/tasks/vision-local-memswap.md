# vision-local: запретить подкачку (memswap_limit) — вторая половина фикса OOM

> **Как применить.** Патч лежит рядом с этим файлом и проверен — ложится чисто:
>
> ```bash
> git pull                                          # чекаут отстаёт на 6 коммитов
> git am docs/tasks/vision-local-memswap.patch
> git push
> ```
>
> Дальше обычный деплой. Правка **уже применена к живому контейнеру** вручную
> (`swap.max = 0`, healthy), но держится только до следующего деплоя: тот
> жёстко сбрасывает дерево на `origin/master` и снесёт её, как уже снёс один
> раз 03.09. Пока правки нет в репозитории, она умирает при каждом деплое.

## Что сделать

В `docker-compose.yml`, сервис `vision-local`, добавить одну строку рядом с существующим `mem_limit`:

```yaml
    mem_limit: 5600m
    memswap_limit: 5600m
```

`-c` и `mem_limit` **не трогать**: комментарии в файле фиксируют замеры, по которым `-c 4096` обрезал бы самый большой реально обслуженный документ (MAX = 4451 токен), а `mem_limit 3800m` заставлял модель буксовать и вылезать за 600 с. Обе величины уже пробовали менять — обе правки неверны.

Патч — `docs/tasks/vision-local-memswap.patch`, применяется `git am` (см. шапку).

## Зачем

Комментарий от 2026-09-02 в этом же файле описывает механизм верно — «the cgroup cap never fired, the HOST ran out» — но **не объясняет, почему cap не срабатывал**.

Docker без `memswap_limit` даёт контейнеру подкачки **вдвое от лимита памяти** — то есть 11,2 ГБ при лимите 5,6. Поэтому `vision-local` оставался внутри своих 5600 МБ **оперативной** памяти (cgroup-OOM корректно молчал), а разницу добирал из свопа **хоста** и выел все 4 ГБ. Только после этого память кончалась у хоста, и ядро выбирало жертву по всей машине:

- `global_oom`, `CONSTRAINT_NONE` — 27 убийств за 02–03.09
- жертвой каждый раз оказывался `llama-server` как самый крупный процесс, но `postgres` был кандидатом наравне с ним
- владельца при этом залило тревогами: 14 сообщений «RAM 91% занято» / «RAM back to 81%» за пять часов, потому что 88–91% — это просто то, как выглядит бокс, пока модель в памяти

С запрещённой подкачкой cgroup под давлением сначала отдаёт **свой** страничный кеш, а превышение лимита убивает процесс **внутри его cgroup**: одна картинка не распознана, контейнер перезапустился, остальное на машине не задето.

## Доказательство

Правка применялась вживую 03.09 и продержалась 4 часа, после чего её снесло деплоем (была внесена в рабочее дерево без коммита — отсюда эта задача). Замеры за это время:

| | до | после |
|---|---|---|
| `memory.swap.max` в cgroup контейнера | 5,87 ГБ | **0** |
| доступно памяти на хосте | 754 МБ | **3562 МБ** |
| подкачка хоста | 4095 / 4095 | 2539 / 4095, сливалась |
| OOM-убийств на хосте | 27 за 48 ч | **0** |
| OOM-убийств внутри cgroup | — | 0 |
| `vision-local` | — | healthy, распознаёт |

После того как деплой откатил правку, подкачка вернулась к 3974 / 4095 в течение часов, и `llama-server` держал в ней 1505 МБ.

## Как проверить после применения

```bash
CID=$(docker inspect -f '{{.Id}}' aibroker-vision-local)
cat /sys/fs/cgroup/system.slice/docker-$CID.scope/memory.swap.max   # ожидается 0
docker inspect -f '{{.HostConfig.Memory}} {{.HostConfig.MemorySwap}}' aibroker-vision-local
# ожидается два одинаковых числа: 5872025600 5872025600
```

Дальше сутки смотреть `free -m`: подкачка должна сливаться, а не забиваться, и `journalctl -k | grep oom` — оставаться пустым.

## Что этой задачей НЕ закрывается

**Хост остаётся слегка переподписан.** 5600 МБ у `vision-local` плюс ~2,2 ГБ у остальных сервисов на 7,56 ГБ физической памяти. Запрет подкачки убирает механизм глобального OOM, но не создаёт запаса.

**Десять контейнеров до сих пор вообще без лимита памяти** — они могут расти неограниченно, и каждому из них docker так же разрешает подкачку:

- `aibroker-api`, `aibroker-monitor`, `aibroker-pgbouncer`, `aibroker-postgres`, `aibroker-redis`
- все пять сервисов `stepan2`

Сейчас они потребляют скромно (api 265 МБ, monitor 91 МБ, postgres 143 МБ, остальные единицы мегабайт), но ничем не ограничены. Это следующий рычаг, и он важнее дальнейшего подкручивания `vision-local`.

## Связанное

Со стороны Vera 3 (репозиторий `zapleoceo/muai`, коммит `1fb8838c`) уже сделано:

- порог тревоги по памяти поднят с 87/93 на 94/97 и вынесен в настройки `monitor_mem_warn_pct` / `monitor_mem_crit_pct` — 88–91% при работающей модели больше не считается аварией
- добавлена проверка **занятости подкачки** (порог 90%), которой не было вовсе. Именно исчерпание свопа, а не процент ОЗУ, предшествовало 27 убийствам — и это состояние было невидимо для монитора
